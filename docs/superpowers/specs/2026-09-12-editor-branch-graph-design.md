# NovelForge — Граф ветвлений — дизайн

## Цель и рамки

`EditorWindow` на `GraphView` (UI Toolkit), read/write визуализация `.nfscript`-скрипта как графа: узлы — блоки текста между `label`-строками, рёбра — переходы `jump`/`gosub`/`choice`-опций между ними. Текст `.nfscript` на диске остаётся единственным источником правды — граф читает и пишет его, не хранит собственное параллельное состояние исполнения.

Входила в исходный список "Инструменты редактора" мастер-спеки (`docs/superpowers/specs/2026-09-05-novelforge-design.md`) как третья часть, после `ScriptedImporter` и окна редактора скрипта (обе уже смержены) и редактора персонажей (тоже смержен, добавлен по итогам первых двух частей).

**Вне рамок этой фазы**:
- Множественный выбор/групповые операции над узлами.
- Zoom-to-fit/minimap как явная задача (это встроенные возможности `GraphView`, но их доводка до полированного состояния не обязательна для этой фазы).
- Undo/redo сверх того, что даёт сам `TextField`/`GraphView` из коробки — как и с `TextArea` в скрипт-редакторе.
- Каскадное удаление ссылающихся рёбер при удалении узла — ссылки становятся битыми (раздел "Битые и недостижимые узлы"), автор чинит вручную.

## Почему это первое использование UI Toolkit в редакторских инструментах

Весь остальной `NovelForge.Editor` (скрипт-редактор, редактор персонажей, `ScriptedImporter`) — на IMGUI. `GraphView` (`UnityEditor.Experimental.GraphView`) реализован поверх UI Toolkit и не имеет IMGUI-аналога с сопоставимой функциональностью (порты, перетаскиваемые рёбра, zoom/pan холста) — писать это на голом IMGUI означало бы заново изобретать `GraphView` вручную. `GraphView`-символы подтверждены встроенными в `UnityEditor.dll` этой версии Unity (6000.6.0f1) — новый пакет не требуется. Потребуется, вероятно, explicit assembly reference на `UnityEditor.GraphView`/UI Toolkit в `NovelForge.Editor.asmdef`, если он не резолвится неявно — проверяется первой же тестовой сборкой на этапе имплементации, не блокирует дизайн.

## Ключевое техническое решение: собственный парсер, не через `ScriptCompiler`

`ScriptCompiler.Compile()` не подходит как источник модели графа: `if/else/endif` разворачивается в низкоуровневые `ConditionalJumpCommand`/`JumpCommand` без памяти об исходной структуре, а имена меток резолвятся в числовые индексы команд (`JumpCommand.TargetIndex` — `int`, не строка) — обратная сериализация в текст с сохранением исходных имён меток из скомпилированной модели невозможна без потери информации.

Вместо этого — новый чистый класс **`Editor/GraphDocumentParser.cs`**, построчный, по духу как `DslSyntaxHighlighter`/`DslAutocompleteProvider`: не резолвит имена меток, не разворачивает `if/else`, не идёт через компиляцию/линковку вообще.

## Модель `GraphDocument`

Гранулярность узла — **один на `label`-блок** (не один на строку): узел = всё содержимое между `label`-строками, снятое целиком, без построчной разбивки на дочерние узлы. Причина: точное соответствие исходному тексту без потери гранулярности реплик/`set`/generic-команд, но без визуальной перегруженности графа на длинных скриптах — то же соотношение сложности/выгоды, что уже выбрано для панели ошибок скрипт-редактора (панель вместо inline-подчёркивания).

```csharp
public class GraphDocument
{
    public IReadOnlyList<GraphNode> Nodes { get; }
}

public class GraphNode
{
    public string LabelName { get; }
    public string Body { get; }                          // текст блока без label-строки и trailing choice/jump/gosub
    public IReadOnlyList<ChoiceOption> Choices { get; }   // пусто, если блок не заканчивается choice
    public string TrailingJumpTarget { get; }             // null, если нет trailing jump/gosub
    public bool TrailingIsGosub { get; }
    public string LeadingComment { get; }                 // комментарий(и) перед label-строкой, если есть
}

public readonly struct ChoiceOption
{
    public string Text { get; }
    public string ExplicitId { get; }   // null, если не указан @id
    public string TargetLabel { get; }
}
```

**Рёбра** выводятся из модели, не хранятся отдельно: `TrailingJumpTarget` (если не null) → одно ребро; каждый `ChoiceOption.TargetLabel` → своё ребро; отсутствие и того и другого при непустом `Body`/отсутствии `return` в конце блока → implicit fall-through ребро к физически следующему в списке `Nodes` узлу (см. ниже).

Комментарии, прицепленные перед строкой (как `pendingComment` в `ScriptCompiler`), хранятся как `LeadingComment` на узле — для round-trip формattер пишет их обратно перед `label`-строкой.

## GraphView-узел: текст + структурные строки-порты

Один `GraphView`-узел на `GraphNode`, две части:
- **Тело** — редактируемое multiline `TextField` с `GraphNode.Body`. Без подсветки синтаксиса в этой версии (переиспользование `DslSyntaxHighlighter` для read-only preview рядом с полем — не в первой итерации, узел и так тесноват; чисто визуальное дополнение, не блокирует функциональность при отсутствии).
- **Структурные строки-порты**, под текстовым полем: одна на каждый `ChoiceOption` (редактируемый `TextField` с текстом варианта + `Port` справа для drag-to-connect) и одна на `TrailingJumpTarget`, если есть (просто `Port`, подпись "jump"/"gosub" по `TrailingIsGosub`). Эти строки перестраиваются при каждом реparse текста тела: правка добавила/убрала `choice`-опцию или trailing jump в тексте → порты появляются/исчезают.

**Fall-through** (блок без `TrailingJumpTarget` и без `Choices`, не заканчивается `return`) — рисуется пунктирным ребром к физически следующему узлу (в отличие от сплошной линии explicit jump/gosub/choice). Перетаскивание этого пунктирного ребра на другой узел дописывает в текст блока явный `jump <новая цель>` — превращает implicit fall-through в explicit jump.

## Сохранение и конфликты

- **Save** — кнопка + авто при потере фокуса окна (как в `NovelScriptEditorWindow`). Канонический форматтер (чистая функция, `GraphDocument` → `string`) сериализует узлы в исходном порядке: `label <name>` → `Body` как есть → structured-строки `Choices`/`TrailingJumpTarget` в каноничном формате (`"текст" [@id] -> label` / `jump label` / `gosub label`) → `LeadingComment`, если был, пишется строкой(ами) `// ...` непосредственно перед `label`.
- **Источник правды** — сам `.nfscript`-файл на диске, не кэш импорта (`NovelScriptAsset.Source`) — тот же принцип, что и в скрипт-редакторе.
- **Конфликт** (файл на диске изменился снаружи, пока в графе есть несохранённые правки) — `EditorUtility.DisplayDialog` с двумя опциями: "Reload from disk" (отбросить правки графа) / "Keep graph, overwrite disk". Простой модальный диалог, без кастомного UI/мержа.
- **Позиции узлов на холсте** — side-car `<script>.nfgraph.meta` рядом со скриптом, JSON `{ "labelName": {"x": ..., "y": ...} }`. Не часть `.nfscript`, не участвует в конфликт-детекции текста скрипта — раскладка теряется независимо от текстовых конфликтов, если сам `.nfgraph.meta` не сохранён.

## Битые и недостижимые узлы

- **Битая ссылка** (`TrailingJumpTarget`/`ChoiceOption.TargetLabel` указывает на несуществующий `LabelName`) — порт рисуется висящим (без ребра), предупреждающим цветом, tooltip "метка '…' не найдена". Не блокирует редактирование ни этого, ни других узлов.
- **Недостижимый узел** (ни один `jump`/`gosub`/choice/fall-through никуда на него не ведёт, и это не первый узел в списке `Nodes`) — рамка/фон узла получает предупреждающий оттенок.
- Ничего не падает на битом/цикличном графе — тот же принцип "не exception наружу", что и во всей остальной обработке ошибок проекта.

## Добавление/удаление узлов

- **Добавить узел** — правый клик по холсту → "Add Label": добавляет пустой `label <auto-имя>` блок в конец текста, сразу переводит имя метки в режим редактирования.
- **Удалить узел** — правый клик по узлу → "Delete": убирает весь label-блок из текста. Ссылки на него из других узлов становятся битыми (см. выше) — без каскадного удаления, автор чинит вручную.
- **Пересоздание jump** — перетаскивание порта trailing-jump/gosub или choice-опции на другой узел переписывает имя целевой метки в тексте (структурная правка через модель, не прямой ввод текста).
- **Переименование метки** — заголовок узла (`LabelName`) редактируется как обычный `GraphView`-заголовок (двойной клик). Переименование НЕ переписывает автоматически ссылающиеся на неё `jump`/`gosub`/choice-опции в других узлах — они становятся битыми (см. раздел выше), автор правит вручную или перетаскиванием портов. Тот же принцип, что и у форматтера: правки текста в одном месте не каскадируют по всему документу сами по себе.

## Тестирование

- **`GraphDocumentParser`** — EditMode-тесты: парсинг label-блоков с реплики/`set`/generic-командами в теле, блок с одним/несколькими `choice`-опциями, блок с trailing `jump`/`gosub`, блок без того и другого (fall-through), `LeadingComment` перед `label`, пустой/некорректный вход не бросает исключение.
- **Canonical formatter** — round-trip тесты: `Serialize(Parse(text)) == text` (с точностью до канонизации пробелов) для набора валидных скриптов; устойчивость к правке модели (переименование метки → все ссылающиеся `ChoiceOption.TargetLabel`/`TrailingJumpTarget` в СЕРИАЛИЗОВАННОМ выводе не переименовываются автоматически — это ответственность отдельного шага "пересоздание jump", не formatter'а; formatter только сериализует то, что есть в модели как есть).
- **`NovelBranchGraphWindow`** (сам `EditorWindow`/`GraphView`) — не тестируется автоматически, как `NovelScriptEditorWindow` и `CharacterEditorWindow`. Живой QA обязателен перед мержем.

## План живой проверки (обязательный шаг этой фазы)

Как и в двух предыдущих частях фазы редакторских инструментов — живой QA через computer-use в реальном Unity Editor, до финального ревью и мержа:
1. Открыть граф на тестовом `.nfscript` с несколькими `label`, `choice`, обычным `jump` и одним fall-through (без trailing jump) — увидеть все узлы, сплошные рёбра explicit-переходов и пунктирное fall-through ребро.
2. Отредактировать текст тела узла — увидеть, что правка сохраняется в модели (переоткрыть/сохранить и проверить файл на диске).
3. Добавить/убрать `choice`-опцию правкой текста — увидеть, что порт соответствующей строки появляется/исчезает.
4. Перетащить порт trailing jump на другой узел — увидеть, что текст блока обновился на новую цель.
5. Сломать ссылку (переименовать целевую метку в другом узле) — увидеть, что порт стал висящим/предупреждающим, ничего не упало.
6. Добавить узел через контекстное меню, удалить узел через контекстное меню — увидеть текстовые изменения в файле.
7. Изменить файл на диске снаружи (например через скрипт-редактор) при несохранённых правках графа — увидеть диалог конфликта, проверить обе опции.
8. Закрыть и переоткрыть граф — убедиться, что раскладка узлов на холсте восстановилась из `.nfgraph.meta`.
